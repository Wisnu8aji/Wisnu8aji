# Wisnu Setyo Aji

### Civil Engineering · Building PAAX

I work from a Civil Engineering perspective and I am building **[PAAX](https://github.com/Wisnu8aji/paax-ai)** — a desktop agent workspace being developed for civil engineering and construction work.

My interest is not simply in adding AI to engineering software. I am interested in the harder question: **what would an agent need in order to participate usefully in real project work?**

Engineering work is full of context. Drawings, spreadsheets, reports, quantities, specifications, site information, assumptions, project history, and professional judgement are connected to one another. A useful engineering agent therefore has to do more than produce a plausible answer. It needs to understand the active project, work with evidence, use the right tools, maintain task state, and make its work reviewable.

That is the problem I am exploring through PAAX.

---

## What I am building

PAAX is currently focused on the **agent foundation and Command Room**.

The Command Room is intended to become the place where an engineer can work with an agent across two connected modes:

- **Chat** for analysis, discussion, planning, evidence, assumptions, and review;
- **Works** for longer execution-oriented tasks that need tools, files, continuity, and tangible outputs.

I want those two sides to feel like one professional workspace rather than separate AI features.

The current work is concentrated on the parts that have to be dependable before deeper engineering automation makes sense: project context, tool use, sessions, file interaction, controlled execution, recovery, desktop reliability, and a clear relationship between what the agent can do and what the engineer must review or approve.

---

## How I think about engineering agents

### The project matters more than the prompt

An isolated prompt does not contain enough information for many engineering tasks. The agent should understand the project it belongs to and be able to work with the relevant context over time.

### Evidence matters more than confidence

In engineering, a fluent answer is not automatically a useful answer. I want PAAX to become increasingly explicit about evidence, assumptions, provenance, uncertainty, and what still requires human judgement.

### An agent should be able to work

The useful boundary is not only question answering. I am interested in agents that can inspect, organize, operate supported tools, work through multi-step tasks, and produce something the engineer can actually use.

### Human responsibility stays visible

The goal is not to hide engineering decisions behind automation. The engineer should remain able to direct the work, understand what happened, inspect outputs, and control consequential actions.

### Build the foundation before pretending the future is finished

PAAX has a much broader engineering direction, but not every future capability is ready to be described as a product feature. Some parts require substantially more research and real project validation. I prefer to keep that uncertainty visible rather than make claims ahead of the work.

## Current areas of focus

My current work around PAAX includes:

- the desktop agent experience;
- Command Room interaction and information hierarchy;
- project-aware context;
- agent tool use and task execution;
- persistent conversations and longer-running work;
- document and evidence workflows;
- engineering-oriented file interaction;
- agent reliability, recovery, and execution boundaries;
- defining a distinct PAAX product identity;
- researching how later civil-engineering capabilities should connect to the agent foundation.

Further engineering directions may eventually include quantity and cost workflows, RAB, drawing and document intelligence, engineering databases, project controls, reporting, and other construction workflows. Those areas are still being researched and should not be treated as finished commitments.

---

## Why I keep building it

Civil engineering has many highly structured workflows, but the information surrounding those workflows is often fragmented. At the same time, modern agents are becoming capable of doing more than answering questions.

I think there is useful territory between those two realities: software that understands enough of the engineering workspace to help organize information, investigate problems, execute bounded tasks, and reduce repetitive project work without pretending to replace professional engineering judgement.

PAAX is my attempt to explore that territory seriously.
